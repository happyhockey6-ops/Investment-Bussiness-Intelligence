# Architectural Decisions

Decisions worth recording because they weren't forced by the requirements —
someone reading the code later should know *why*, not just *what*.

## Why a modular monolith, not microservices

Phase 0 has zero real traffic and zero real query patterns. Splitting into
services now would mean guessing at boundaries under no load information,
paying operational cost (deployment, networking, cross-service
transactions) for no benefit yet, and making refactoring the domain
boundaries themselves (which is expected during early phases) much more
expensive. The modular-monolith package structure keeps the *option* to
extract a service later — each `ibi.<domain>` package already has an
explicit interface — without paying for it now.

## Why Python

Chosen for: strong typing via `pydantic`/dataclasses for the evidence and
epistemic model, `SQLAlchemy`/`Alembic` as a mature ORM/migration story
(explicitly requested), the `Decimal` type for correct financial arithmetic,
and broad ecosystem support for the data/ML work later phases will need. No
other language was seriously evaluated for Phase 0 — revisit only if a
specific later requirement (e.g. a latency-critical market-data path)
demands it.

## Why domain logic is not implemented in Phase 0

Every prior "obvious" design decision (schema shape, provider interface
shape) gets harder to change once real business logic and stored data
depend on it. Phase 0 optimizes for getting the boundaries right first;
filling them in is comparatively cheap and low-risk once the shape is
proven by real usage in Phase 1+.

## Why `financial_engine` has real (not stubbed) metrics

A pure-interface Phase 0 would leave the "financial calculations must be
deterministic, not AI-generated" principle undemonstrated. Implementing
`revenue_growth`, `gross_margin`, `free_cash_flow`, and `roic` with real
tests proves the `MetricCalculation` pattern (typed inputs,
`Uncertain`-on-undefined-arithmetic, no I/O) end-to-end, so later metrics
are additive rather than requiring a design change.

## Why `Uncertain` is a union of distinct types, not one `None`

`Unknown`, `InsufficientEvidence`, and `ConflictingEvidence` are different
situations that a decision-maker should treat differently — "never looked
up" is not the same operational problem as "sources disagree". Collapsing
them to `None` (which is also used for "field does not apply") would lose
that distinction and make it easy to accidentally treat a real unknown as
a false negative.

## Why PostgreSQL + a single relational schema (not a graph database) for the Knowledge Graph

`ibi.knowledge_graph` is currently backed by ordinary relational tables (see
`db.models`). A dedicated graph database may be justified once real
multi-hop relationship queries exist, but Phase 0 has none — adding one now
would be infrastructure without a justified query pattern (see "Avoid
premature microservices/infrastructure" in the Phase 0 charter). **Open
question**, revisit once `knowledge_graph` has real usage.

## Why the initial Alembic migration is hand-written, not autogenerated

No live PostgreSQL instance was available in this environment at the time
this migration was written (confirmed during the Phase 0 remediation
audit: no `postgres` service, no process, no listener on port 5432, no
Docker on this machine). `alembic revision --autogenerate` diffs against a
real connected database; without one, the only options were to skip the
migration entirely or write it by hand from the model definitions and
verify it against SQLite (see `tests/integration/test_alembic_migration.py`).
The migration was verified to create every table `Base.metadata` declares,
and during the remediation audit every column's type and nullability was
cross-checked by hand, column-by-column, between the ORM models and the
migration — no discrepancies found.

**Update**: a real PostgreSQL 18.6 instance later became available. This
migration (`50445f5a9e59`) was run against it directly
(`alembic upgrade head`), and a subsequent `alembic check` reported "No new
upgrade operations detected" — confirming zero drift between this
hand-written migration and the ORM models on real PostgreSQL, independent
of the manual cross-check above. The Phase 0 baseline is now
**PostgreSQL-verified**. The two Phase 1 migrations
(`50dc0583f9c1`, `a950c85c80b9`) have since had the same live-PostgreSQL
run performed and are **also PostgreSQL-verified** — see "Phase 1: SEC
EDGAR ingestion" below for the full result.

## Why JSON columns use a JSONB variant, not plain JSON

Found during the Phase 0 remediation audit: all JSON-typed columns
(`observations.value`, `theses.evidence_ids`,
`scenarios.{assumptions,catalysts,risks,unknowns,invalidation_conditions}`)
originally used plain `sa.JSON`, which PostgreSQL stores as its older
text-based `json` type rather than the indexable, binary `jsonb` type —
`jsonb` is the type PostgreSQL's own documentation recommends for new
columns. Fixed via `ibi.db.base.portable_json()`, which uses
`JSON().with_variant(JSONB(), "postgresql")`: `jsonb` on PostgreSQL, plain
`JSON` everywhere else (so SQLite-based tests are unaffected). No new
dependency was needed — `sqlalchemy.dialects.postgresql` ships with
SQLAlchemy core.

## Why AI provider defaults to `none`

The platform must be usable, testable, and demonstrably correct with zero
AI spend and zero vendor dependency. Defaulting `IBI_AI_PROVIDER=none`
(backed by `NullAIProvider`, which raises `ProviderError` rather than
silently no-op-ing) makes "deterministic-only mode" the default state
rather than an edge case, and it means Phase 0's entire test suite runs
without any API key.

## Why no production market-data vendor was selected

Every real market-data vendor has different rate limits, data quality,
survivorship-bias handling, and cost structure. Choosing one before any
`market_engine`/`backtesting_engine` logic exists to consume it would be a
guess locked in early. `NullMarketDataProvider` (always returns `Unknown`)
keeps the interface exercised without committing to a vendor.

## Phase 0 scope classification (remediation audit)

Performed as part of the Phase 0 remediation/final-audit pass, reviewing
everything implemented against the charter's "boundaries and foundations,
not Phase 1+ functionality" mandate:

| Area | Classification | Why |
|---|---|---|
| `financial_engine` (4 metrics: `revenue_growth`, `gross_margin`/`gross_profit`, `free_cash_flow`, `roic`) | **FOUNDATION / ACCEPTABLE** | Implemented specifically to prove the determinism pattern (typed inputs, `Uncertain`-on-undefined-arithmetic, no I/O, no AI call) end-to-end with real tests — not as a step toward a complete financial engine. Deliberately not expanded further in this pass. See "Financial-engine scope" below for the architectural-risk assessment. |
| `providers.ai` (`ClaudeProvider`, `LocalAIProvider`) | **FOUNDATION / ACCEPTABLE** | Both raise `NotImplementedError` on the one method that would do real work (`complete`). | `providers.ai` (`NullAIProvider`) / `providers.market_data` (`NullMarketDataProvider`) | **FOUNDATION / ACCEPTABLE** | Fully implemented, but both are deliberately inert: one refuses every request, the other returns only `Unknown`. Neither performs I/O, holds a vendor dependency, or selects a production vendor. |
| `db.models` (16 tables) + Alembic migration | **FOUNDATION / ACCEPTABLE** | Directly implements the schema categories the charter itself named (see docs/data_architecture.md's "Exact table inventory" for the 14-category → 16-table reconciliation). No speculative tables beyond that were added. |
| The other 17 domain packages (`data_engine`, `entity_engine`, `market_engine`, `macro_engine`, `event_engine`, `knowledge_graph`, `signal_engine`, `ai_research_engine`, `thesis_engine`, `red_team`, `backtesting_engine`, `learning_engine`, `valuation`, `scoring`, `alert_engine`, `decision_engine`, `dashboard`) | **FOUNDATION / ACCEPTABLE** | Interfaces and dataclasses only — every concrete method either doesn't exist or raises `NotImplementedError`/is an unimplemented `ABC` method. found exceeds the charter's foundation-only mandate.

### Financial-engine scope and risk

The four implemented metrics were a deliberate choice to make the
"deterministic computation, not AI, calculates financial metrics"
principle verifiable rather than aspirational — an interface with no
implementation cannot be tested for determinism. They are not, and are not
intended to be, a usable subset of a real financial engine: they are not
wired to any data source, are exercised only by synthetic `Decimal` values
in unit tests, and no production code path calls them. **Architectural
risk: low.** They are pure functions with no side effects, no shared
mutable state, and no dependency any other unimplemented engine currently
relies on — removing or changing them would not ripple anywhere. The risk
worth naming is a *process* one, not a code one: it would be easy for a
future contributor to keep "just adding one more metric" to this module
outside a deliberate Phase 1 planning decision. This pass did not expand
them, per instruction, and any further metric should be a deliberate
Phase 1 scoping decision, not an incremental addition.

## Phase 1: SEC EDGAR ingestion

The first real `data_engine` source went through four review passes before
implementation was authorized. Recorded here so the reasoning survives
independent of that conversation.

### XBRL fact identity — empirical validation

Initial proposed key `(entity_id, metric_id, period_end_date, accession_number)`
was rejected: a single XBRL tag can report both an annual and a
quarter-only duration ending on the same date within the same accession
(e.g. `Revenues` reported as both a full fiscal year and a Q4-only
duration), which the flawed key cannot distinguish. Revised to
`(entity_id, taxonomy, tag, unit, start_date, end_date, accession_number)`
— `metric_id` in the schema encodes `"taxonomy:tag"` together, so this is
one column, not two. **Empirically validated** (not just reasoned about)
against real `companyfacts` data for Apple and Microsoft — ~58,000 real
fact entries, **zero collisions** on the full key; the flawed key collided
2,517 times (AAPL) and 4,823 times (MSFT), confirming the failure mode was
real, not hypothetical. Enforced via two partial unique indexes rather than
a single `COALESCE`-based index or a NULL-sentinel column — see the
docstring on `FinancialDataPointRecord.__table_args__` for why (self
-documenting per fact shape; avoids a duration fact whose `start_date`
happens to equal its `end_date` colliding with an instant fact by
coincidence, a risk under the `COALESCE` approach).

### Point-in-time availability — hybrid rule

`retrieval_date` (when *we* fetched something) must never be used as a
proxy for public availability — using it as the primary backtest filter
would be wrong in both directions once ingestion backfills history (a
2015 filing would falsely appear "unknowable" until whenever the ingestion
job happened to run).

The approved rule, grounded in official SEC documentation
(sec.gov/submit-filings/filer-support-resources/how-do-i-guides/determine-status-my-filing
and sec.gov/submit-filings/filer-support-resources/edgar-calendar, both
fetched and quoted during the review):

1. If `acceptanceDateTime` is present, its America/New_York local time
   falls within EDGAR's documented operating hours (06:00-22:00), and that
   date is an SEC/federal business day: use it directly
   (`availability_precision="acceptance_timestamp"`). SEC's own
   documentation ties acceptance and dissemination together within this
   window and explicitly *decouples* them outside it ("will not be
   disseminated by EDGAR until the next business day" for after-hours
   submissions) — so a timestamp outside the window is not trusted.
2. Otherwise: 00:00 America/New_York on the next SEC/federal business day
   after `filing_date` (`availability_precision="day_conservative"`).

The federal holiday calendar (`ibi.data_engine.sec_edgar.holidays`) is
computed from each holiday's defining rule (nth-weekday-of-month, or a
fixed date with the standard weekend-observance shift) rather than
hand-enumerated per year, to avoid transcription error across the
multi-decade range ingested SEC data spans. SEC/EDGAR follows the *federal*
holiday calendar, not the NYSE market calendar (federal observes Columbus
Day and Veterans Day; NYSE does not) — deliberate, since the rule reasons
about SEC dissemination, not market trading days.

**Honesty about what's not verified**: no SEC document was found that
quantifies an exact accept-to-dissemination lag for ordinary business-hours
filings (only the after-hours edge case is explicitly quantified). The rule
does not claim second-level precision beyond what's documented — see
`ibi.data_engine.sec_edgar.availability`'s docstring.

### Provenance — two distinct, non-conflated edges

`financial_data.accession_number` (+ the `filings` table) answers "what
filing produced this" — filing identity. `financial_data.source_document_id`
answers "which raw API snapshot did we read this value from" — a different
question, since one `companyfacts` snapshot aggregates facts from many
filings. Phase 1 does not fetch or store the original filing's HTML/XML
bytes; only SEC's own filing metadata and aggregated XBRL facts.

### Why exactly two companies in the fixed universe

Apple (CIK 320193) and Microsoft (CIK 789019) — both large, stable,
extremely well-documented CIKs (low risk of a wrong identifier), giving
genuinely varied real data (Apple's real data includes the annual/quarterly
duration collision case above) without needing a general entity resolver.
A third, more obscure company was considered and rejected for this pass —
better to keep the controlled universe to companies whose identifiers are
beyond doubt.

### Why the SEC HTTP client uses stdlib `urllib`, not a new dependency

SEC's JSON APIs are plain GETs; `urllib.request` handles headers, timeouts,
and retry logic (hand-rolled) without adding `httpx`/`requests` to
`pyproject.toml`. Revisit only if a real need (connection pooling, async)
emerges.

### PostgreSQL validation status for Phase 1 migrations

**Complete.** Both Phase 1 migrations (`50dc0583f9c1`: `filings` table +
`financial_data` columns; `a950c85c80b9`: the two partial unique indexes)
were initially verified against SQLite only
(`tests/integration/test_alembic_migration.py`,
`test_sec_edgar_ingestion.py`'s DB-level constraint tests), then
subsequently run against the real PostgreSQL 18.6 instance:

- Migrated to head (`a950c85c80b9`) successfully.
- `alembic check` reported "No new upgrade operations detected" — zero
  drift between the migrations and the ORM models on real PostgreSQL.
- Direct read-only inspection confirmed all 18 tables (17 application
  tables + `alembic_version`) exist, matching `Base.metadata` exactly.
- Direct inspection of `financial_data`'s indexes confirmed exactly three:
  `financial_data_pkey`, `uq_financial_data_duration_fact`,
  `uq_financial_data_instant_fact` — the partial unique indexes exist on
  real PostgreSQL with the expected names, not just on SQLite.

The partial-index approach (standard PostgreSQL, unlike the SQLite
`ALTER COLUMN ... DROP DEFAULT` incompatibility caught and fixed via
`batch_alter_table` during implementation) carried low risk going in; this
result confirms it rather than merely assuming it. See DEVELOPMENT.md for
the procedure, kept for reproducibility.

## Phase 2B: calculation results

Design went through three review revisions before implementation was
authorized. Implementation follows the consolidated design's
recommendations as defaults, with these explicit owner decisions:

| # | Approved decision | Where |
|---|---|---|
| C1 | Fail closed when no single accession is a complete, consistent basis; never mix bases (`NO_SINGLE_BASIS`) | `resolver.resolve` |
| C2 | Record new evidence and confirmations only when they change the resolved state or provenance; no redundant rows | per-period hash dedupe; append-only rows per version pair (no copying across generations) |
| C3 | Retroactive drift is an error; historical results are never rewritten; remedy is an explicit new policy version or a separately approved recovery | `RetroactiveDriftError` |
| C4 | Read-only check of the live database first; without original snapshots, existing facts are neither updated nor given invented form types | No backfill implemented (see below) |
| C5 | Portable, tested CHECK constraints on the new result tables | migration `e7f3a2c91b40` |
| C6 | Validate the 8-K/form behaviour on full live SEC data for AAPL/MSFT, in memory only, nothing persisted | `tests/integration/test_phase2b_full_data_live.py` (opt-in) |
| C7 | Strict fail-closed for divergence from other/unknown forms | `UNCLASSIFIED_FORM_DIVERGENCE` |
| C8 | Exact `Decimal` equality, no tolerances | resolver, identity checks |
| C9 | `NUMERIC(28,10)`, explicit half-even rounding in Python | `formulas.quantize_result` |

Also required: facts and calculations stay separate (`financial_data` is
facts-only; results in `metric_results`, provenance in
`metric_result_inputs`); the three-tier form policy, including eligible
complete 8-K/8-K/A recasts; every historical query takes an explicit version
pair and never mixes pairs.

### 8-K eligibility: implemented, but no Phase 2B evidence source qualifies one

An 8-K/8-K/A becomes a basis candidate only if both of these hold:

- it carries every evidence kind the policy requires; and
- every identity check of the metric can be evaluated inside the 8-K and
  passes (`resolver._is_eligible_basis`).

A complete set of tags is never sufficient on its own. An eligible 8-K
basis is annotated `revision_kind = recast`. Tests cover the qualifying
path and every way it can fail.

Policy v1 requires `xbrl_instance_restatement_classified`. That
classification needs the filing's own XBRL instance (dimensional
restatement members, error-correction flags), which companyfacts drops and
Phase 2B does not ingest. So `results_store.RECAST_EVIDENCE` is
deliberately empty, and under v1 no 8-K qualifies yet. 8-K facts corroborate
when they are equal; when they diverge, the result is
`UnverifiedRevision(UNCLASSIFIED_8K_DIVERGENCE)`.

Supplying real evidence later means two things:

- an approved new evidence source; and
- feeding its classifications in as a hashed snapshot input, which changes
  `input_set_hash` and therefore requires a new policy version under C3.

It is never an inference from tags.

### Implementation-time reconciliation (second authorization)

Before implementation I checked the uncommitted draft against the final
authorization and found four gaps. All four were corrected; none required
stopping.

1. **Provenance table name.** The draft named it `metric_result_evidence`.
   It is renamed to `metric_result_inputs` as required. It still stores
   every relation, not only inputs.
2. **C2 (no redundant rows).** The draft copied a metric's full history
   into every generation. Under C3, history before a generation's last
   epoch can never change, so results are now append-only per version
   pair. Each row is written once, by the generation that first produced
   it, and a generation's view is the pair's rows with
   `generation_id <= g`.
3. **8-K eligibility path.** The draft hard-wired "never eligible". It is
   now a real, tested eligibility gate driven by the policy's required
   evidence kinds.
4. **Explicit version pairs.** The draft's `read_active` and system-time
   reads inferred the pair from activations. All reads now take a
   `VersionPair`. `active_versions()` only looks one up, and
   `require_values` rejects a series that mixes pairs.

**Migration ID.** Because the schema changed, the uncommitted draft
migration `c2b7e4f19a6d` was replaced by `e7f3a2c91b40` with a new revision
id. If the draft was ever applied somewhere, Alembic fails loudly instead
of silently accepting a different schema.

### Pre-implementation consistency review — findings and resolutions

1. **C3 differs from revision 3's recommendation.** Revision 3 proposed
   that retroactive changes create a new generation pending review. The
   owner chose to block them instead. Implemented as chosen, so the review
   table was not built.
2. **Blocking could leave a stale generation readable.** A blocked build
   leaves the previous generation in place, and the current-knowledge
   reader could have served it as if it were up to date. To prevent that,
   `read_current` checks for facts, quarantines and 4.02 filings the
   generation never saw that are available by `as_of`, and returns
   `UnverifiedRevision(GENERATION_BEHIND_INPUTS)` when it finds any.
3. **`server_default=now()` for new tables (revision 3, C13) was not
   applied.** System-time reads compare generation, activation and fact
   `created_at` values against each other. Mixing a database clock on the
   new tables with the application clock on existing ones would make those
   comparisons inconsistent, so every table keeps the application clock.
   The `TimestampMixin` docstring, which wrongly said "set in the
   database", was corrected.
4. **Phase 1 rows have no form type.** Rows ingested before Phase 2B have a
   NULL `source_form_type`, and re-ingestion never fills it, because the
   duplicate check skips existing facts. The resolver treats NULL as an
   unclassified form, so those facts can never be a basis and their
   divergence fails closed. Any backfill is a separate decision.
5. **4.02 non-reliance has no lookback window in the evidence.** The
   affected periods can't be determined from metadata. The most
   conservative scope is implemented: every period ending before the 8-K's
   filing date, until a later periodic basis supersedes it. Item coverage
   is limited to the submissions "recent" window, and every result records
   this as `non_reliance_scan = submissions_recent_window_only`.
6. **Quarantine is retroactive by nature.** Removing a fact from history is
   blocked under C3 just like any other retroactive change, so recovery
   from a bad fact also needs an explicit new policy version or a
   separately approved recovery procedure. This follows directly from C3.

### Scope implemented vs deferred

- **Implemented:**
  - single-period metrics `ibi:gross_margin` and `ibi:free_cash_flow`
    (calculation version "1", policy "1");
  - generations with append-only results per version pair, typed readers
    M1/M2/M3 taking explicit version pairs, quarantine, and version
    activation lookup;
  - the evidence-gated 8-K eligibility path (no qualifying evidence source
    in Phase 2B);
  - the per-entity advisory lock, shared by ingestion and builds;
  - form type and 8-K items stored at ingestion, with a companyfacts vs
    submissions form-consistency check (`FormTypeMismatchError`, isolated
    per entity).
- **Deferred:**
  - **ROIC:** the NOPAT and invested-capital definitions are not approved.
  - **Cross-period metrics:** deferred by design.
  - **Paginated older submissions history (`filings.files[]`):** the page
    format could not be verified live, because no SEC User-Agent is
    configured in this environment, and implementing it from memory would
    risk ingestion integrity.
  - **Ingesting filing XBRL instances.**
- **Pending review:** the concept→tag map v1 (`policy._CONCEPTS_V1`) needs
  analyst review before production use.

### Validation status (at implementation time)

- **SQLite:** full suite passing, including migration up/down/up and
  `alembic check` with no drift against a fresh database.
- **PostgreSQL:** **not validated.**
  - The existing configuration could not connect, and no credentials were
    requested or guessed.
  - The new store tests run on PostgreSQL only against a dedicated database
    named in `IBI_TEST_POSTGRES_URL`, never against `IBI_DATABASE_URL`.
- **Live database contents:** whether it holds Phase 1 facts is **unknown**.
  See DEVELOPMENT.md for the read-only check.
- **Full-data SEC validation (C6):** **not run**, because
  `IBI_SEC_USER_AGENT` is not set. The test is ready to run opt-in.

## Open questions requiring a human decision

- Which market-data vendor(s) to integrate first, and budget for it.
- Whether/when the Knowledge Graph needs a dedicated graph database.
- Which local model runtime (if any) `LocalAIProvider` should target.
- Concrete AI budget ceiling and enforcement policy (`router.MonthlyBudgetTracker`
  is currently a no-op).
- Hosting/deployment target for PostgreSQL (local dev only vs. managed
  service) — not addressed in Phase 0.
- Whether/when to add database-level `CHECK` constraints (e.g. confidence
  ranges, enum-value membership) and indexes on foreign-key columns — see
  docs/data_architecture.md's PostgreSQL-specific review. Deferred
  intentionally rather than added speculatively. (Phase 2B added CHECKs to
  its new tables only.)
- Phase 2B: whether existing Phase 1 `financial_data` rows (if any exist in
  the live database) should get `source_form_type`, and by what
  provenance-verified procedure.
- Phase 2B: review of the concept→tag map v1; definitions for ROIC;
  whether to ingest paginated submissions history and filing XBRL
  instances (required before any 8-K can qualify as a basis).
