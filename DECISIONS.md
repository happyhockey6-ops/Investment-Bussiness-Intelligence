# Architectural Decisions

Decisions worth recording because they weren't forced by the requirements —
someone reading the code later should know *why*, not just *what*.

## Why a modular monolith, not microservices

Phase 0 has zero real traffic and zero real query patterns. Splitting into
services now would mean guessing at boundaries under no load information,
paying operational cost (deployment, networking, cross-service
transactions) for no benefit yet, and making refactoring the domain
boundaries themselves (which is expected during early phases) much more
expensive. The modular-monolith package structure keeps the *option* to
extract a service later — each `ibi.<domain>` package already has an
explicit interface — without paying for it now.

## Why Python

Chosen for: strong typing via `pydantic`/dataclasses for the evidence and
epistemic model, `SQLAlchemy`/`Alembic` as a mature ORM/migration story
(explicitly requested), the `Decimal` type for correct financial arithmetic,
and broad ecosystem support for the data/ML work later phases will need. No
other language was seriously evaluated for Phase 0 — revisit only if a
specific later requirement (e.g. a latency-critical market-data path)
demands it.

## Why domain logic is not implemented in Phase 0

Every prior "obvious" design decision (schema shape, provider interface
shape) gets harder to change once real business logic and stored data
depend on it. Phase 0 optimizes for getting the boundaries right first;
filling them in is comparatively cheap and low-risk once the shape is
proven by real usage in Phase 1+.

## Why `financial_engine` has real (not stubbed) metrics

A pure-interface Phase 0 would leave the "financial calculations must be
deterministic, not AI-generated" principle undemonstrated. Implementing
`revenue_growth`, `gross_margin`, `free_cash_flow`, and `roic` with real
tests proves the `MetricCalculation` pattern (typed inputs,
`Uncertain`-on-undefined-arithmetic, no I/O) end-to-end, so later metrics
are additive rather than requiring a design change.

## Why `Uncertain` is a union of distinct types, not one `None`

`Unknown`, `InsufficientEvidence`, and `ConflictingEvidence` are different
situations that a decision-maker should treat differently — "never looked
up" is not the same operational problem as "sources disagree". Collapsing
them to `None` (which is also used for "field does not apply") would lose
that distinction and make it easy to accidentally treat a real unknown as
a false negative.

## Why PostgreSQL + a single relational schema (not a graph database) for the Knowledge Graph

`ibi.knowledge_graph` is currently backed by ordinary relational tables (see
`db.models`). A dedicated graph database may be justified once real
multi-hop relationship queries exist, but Phase 0 has none — adding one now
would be infrastructure without a justified query pattern (see "Avoid
premature microservices/infrastructure" in the Phase 0 charter). **Open
question**, revisit once `knowledge_graph` has real usage.

## Why the initial Alembic migration is hand-written, not autogenerated

No live PostgreSQL instance was available in this environment (confirmed
during the Phase 0 remediation audit: no `postgres` service, no process, no
listener on port 5432, no Docker on this machine).
`alembic revision --autogenerate` diffs against a real connected database;
without one, the only options were to skip the migration entirely or write
it by hand from the model definitions and verify it against SQLite (see
`tests/integration/test_alembic_migration.py`). The migration was verified
to create every table `Base.metadata` declares, and during the remediation
audit every column's type and nullability was cross-checked by hand,
column-by-column, between the ORM models and the migration — no
discrepancies found. **Follow-up, still outstanding**: run
`alembic revision --autogenerate` against a real PostgreSQL instance once
one exists, as a final confirmation independent of this manual check — see
the exact procedure in DEVELOPMENT.md. Until that runs, treat the schema as
SQLite-verified, PostgreSQL-unverified.

## Why JSON columns use a JSONB variant, not plain JSON

Found during the Phase 0 remediation audit: all JSON-typed columns
(`observations.value`, `theses.evidence_ids`,
`scenarios.{assumptions,catalysts,risks,unknowns,invalidation_conditions}`)
originally used plain `sa.JSON`, which PostgreSQL stores as its older
text-based `json` type rather than the indexable, binary `jsonb` type —
`jsonb` is the type PostgreSQL's own documentation recommends for new
columns. Fixed via `ibi.db.base.portable_json()`, which uses
`JSON().with_variant(JSONB(), "postgresql")`: `jsonb` on PostgreSQL, plain
`JSON` everywhere else (so SQLite-based tests are unaffected). No new
dependency was needed — `sqlalchemy.dialects.postgresql` ships with
SQLAlchemy core.

## Why AI provider defaults to `none`

The platform must be usable, testable, and demonstrably correct with zero
AI spend and zero vendor dependency. Defaulting `IBI_AI_PROVIDER=none`
(backed by `NullAIProvider`, which raises `ProviderError` rather than
silently no-op-ing) makes "deterministic-only mode" the default state
rather than an edge case, and it means Phase 0's entire test suite runs
without any API key.

## Why no production market-data vendor was selected

Every real market-data vendor has different rate limits, data quality,
survivorship-bias handling, and cost structure. Choosing one before any
`market_engine`/`backtesting_engine` logic exists to consume it would be a
guess locked in early. `NullMarketDataProvider` (always returns `Unknown`)
keeps the interface exercised without committing to a vendor.

## Phase 0 scope classification (remediation audit)

Performed as part of the Phase 0 remediation/final-audit pass, reviewing
everything implemented against the charter's "boundaries and foundations,
not Phase 1+ functionality" mandate:

| Area | Classification | Why |
|---|---|---|
| `financial_engine` (4 metrics: `revenue_growth`, `gross_margin`/`gross_profit`, `free_cash_flow`, `roic`) | **FOUNDATION / ACCEPTABLE** | Implemented specifically to prove the determinism pattern (typed inputs, `Uncertain`-on-undefined-arithmetic, no I/O, no AI call) end-to-end with real tests — not as a step toward a complete financial engine. Deliberately not expanded further in this pass. See "Financial-engine scope" below for the architectural-risk assessment. |
| `providers.ai` (`ClaudeProvider`, `LocalAIProvider`) | **FOUNDATION / ACCEPTABLE** | Both raise `NotImplementedError` on the one method that would do real work (`complete`). They exist to prove the `AIProvider` interface is implementable by more than one vendor shape. No AI SDK dependency was added (`pyproject.toml` has none) and no API call has ever been made. |
| `providers.ai` (`NullAIProvider`) / `providers.market_data` (`NullMarketDataProvider`) | **FOUNDATION / ACCEPTABLE** | Fully implemented, but both are deliberately inert: one refuses every request, the other returns only `Unknown`. Neither performs I/O, holds a vendor dependency, or selects a production vendor. |
| `db.models` (16 tables) + Alembic migration | **FOUNDATION / ACCEPTABLE** | Directly implements the schema categories the charter itself named (see docs/data_architecture.md's "Exact table inventory" for the 14-category → 16-table reconciliation). No speculative tables beyond that were added. |
| The other 17 domain packages (`data_engine`, `entity_engine`, `market_engine`, `macro_engine`, `event_engine`, `knowledge_graph`, `signal_engine`, `ai_research_engine`, `thesis_engine`, `red_team`, `backtesting_engine`, `learning_engine`, `valuation`, `scoring`, `alert_engine`, `decision_engine`, `dashboard`) | **FOUNDATION / ACCEPTABLE** | Interfaces and dataclasses only — every concrete method either doesn't exist or raises `NotImplementedError`/is an unimplemented `ABC` method. No domain logic. |
| Anything resembling ingestion, live research, UI, trading, or vendor selection | **NOT PRESENT** | Confirmed absent by inspection — there is no code path that ingests real data, calls a real AI/market-data API, renders a UI, or selects a production vendor. |

No item was classified **OUT OF SCOPE** or **REQUIRES REVIEW** — nothing
found exceeds the charter's foundation-only mandate.

### Financial-engine scope and risk

The four implemented metrics were a deliberate choice to make the
"deterministic computation, not AI, calculates financial metrics"
principle verifiable rather than aspirational — an interface with no
implementation cannot be tested for determinism. They are not, and are not
intended to be, a usable subset of a real financial engine: they are not
wired to any data source, are exercised only by synthetic `Decimal` values
in unit tests, and no production code path calls them. **Architectural
risk: low.** They are pure functions with no side effects, no shared
mutable state, and no dependency any other unimplemented engine currently
relies on — removing or changing them would not ripple anywhere. The risk
worth naming is a *process* one, not a code one: it would be easy for a
future contributor to keep "just adding one more metric" to this module
outside a deliberate Phase 1 planning decision. This pass did not expand
them, per instruction, and any further metric should be a deliberate
Phase 1 scoping decision, not an incremental addition.

## Open questions requiring a human decision

- Which market-data vendor(s) to integrate first, and budget for it.
- Whether/when the Knowledge Graph needs a dedicated graph database.
- Which local model runtime (if any) `LocalAIProvider` should target.
- Concrete AI budget ceiling and enforcement policy (`router.MonthlyBudgetTracker`
  is currently a no-op).
- Hosting/deployment target for PostgreSQL (local dev only vs. managed
  service) — not addressed in Phase 0.
- Whether/when to add database-level `CHECK` constraints (e.g. confidence
  ranges, enum-value membership) and indexes on foreign-key columns — see
  docs/data_architecture.md's PostgreSQL-specific review. Deferred
  intentionally rather than added speculatively.
